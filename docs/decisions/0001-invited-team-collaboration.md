# ADR-0001：受邀请团队协作与记录模型

- 状态：已接受
- 日期：2026-08-13
- 决策人：项目负责人

## 背景

Atlas ELN 将从单浏览器本地原型逐步迁移为可通过公网访问的服务器端应用。测试版需要明确最小身份边界、团队权限和实验记录事实源，避免在数据库设计和前端模块化过程中产生多套不兼容模型。

已确认一个计划只对应一次实验，测试版附件只预留接口。

## 决策

### 1. 访问与邀请

- 系统不允许匿名使用；
- 由团队管理员填写受邀人的邮箱；
- 每个邀请链接只能成功接受一次；
- 邀请自创建起 7 天后过期；
- 管理员可在接受前撤销邀请；
- 服务器只保存邀请令牌的哈希；
- 接受邀请时，已登录身份的邮箱必须与邀请邮箱匹配。

### 2. 团队角色

测试版只使用：

- `owner`：管理团队资料、邀请、成员和团队内全部项目；
- `member`：查看并编辑团队内全部项目。

测试版暂不提供项目级权限、只读角色或自定义角色。只有出现明确业务需求后才扩展权限矩阵。

### 3. 实验记录

- 每个计划最多拥有一份当前 Markdown 文档；
- Markdown 文档是实验内容的主要正文；
- `Entry` 是关键事件时间线，用于记录计划、过程、结果、分析和决策等事件；
- `Entry` 不复制整份 Markdown 文档；
- 文档和时间线记录均属于团队项目，所有读写必须在服务端检查成员权限；
- 文档使用版本号进行乐观并发控制，避免协作者静默覆盖。

## 后果

### 正面影响

- 测试版权限模型简单，容易实现和验证；
- 数据库可围绕团队作为隔离边界设计；
- Markdown 与 Entry 各自职责明确，不再构成两个竞争事实源；
- 邀请具备过期、撤销和一次性使用的基本安全属性；
- 后续可以在不改变核心模型的情况下增加 viewer 或项目级角色。

### 限制

- `member` 权限较宽，不适合需要项目级隔离的团队；
- 依靠身份邮箱匹配邀请，身份提供方必须返回已验证且稳定的邮箱；
- 当前不满足正式电子签名、审批和受监管审计要求；
- 文档版本历史的保留数量和生命周期仍需在实现阶段确定。

## 被否决的替代方案

- 匿名公网访问：不符合受邀请用户边界；
- 可长期转发的团队邀请链接：无法可靠限制受邀身份；
- 测试版直接设计复杂 RBAC：增加实现和测试成本但没有已确认场景；
- 只保存 Markdown 或只保存 Entry：不能同时满足连续实验正文和关键事件时间线；
- 浏览器与服务器长期双写：容易产生冲突和事实源不一致。

## 实施约束

- 客户端传来的用户、团队或角色信息不能作为授权依据；
- 每个服务端读取和写入必须从可信身份解析当前用户，并验证团队成员关系；
- 邀请接受必须在单次原子操作中验证状态、邮箱和过期时间，然后创建成员关系并标记邀请已使用；
- 后续改变邀请、角色或记录模型时，应创建新的 ADR，不直接改写本决策的历史结论。
