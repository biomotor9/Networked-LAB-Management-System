# Atlas ELN 服务端迁移计划

> 状态：渐进迁移进行中；当前完成阶段 1、阶段 2 核心范围、阶段 3、阶段 4 和阶段 5 核心范围。

## 1. 迁移原则

采用渐进迁移，不进行一次性重写。每个业务领域在一次明确发布中从浏览器切换到服务器；切换后服务器是该领域唯一事实源，不做长期双写，也不在测试版实现离线双向同步。

目标架构：Next.js 单体应用 + PostgreSQL + 对象存储抽象，通过 Docker 部署到现有 Linux 服务器。Cloudflare Workers、D1 和 R2 不再是当前部署前提。

## 2. 阶段状态

### 阶段 0：产品契约（已完成）

- 仅管理员创建账户；
- owner/member 两级角色；
- 一个计划对应一次实验；
- Markdown 为正文、Entry 为关键事件；
- 附件只预留接口。

### 阶段 1：前端模块化与本地备份（已完成）

- 抽出共享模型、计划树、依赖环检测、Markdown 编解码；
- 建立 `WorkspaceRepository` 与版本化 JSON 备份；
- 补充领域和持久化单元测试；
- 保持现有工作区行为。

### 阶段 2：自托管、身份与团队（核心范围已完成）

- 标准 Next.js standalone 构建和 Docker Compose；
- PostgreSQL、Drizzle Schema、迁移和健康检查；
- 管理员引导创建、登录、强制首次改密和退出；
- owner 创建成员、停用/启用、重置临时密码；
- HttpOnly 哈希会话、服务端角色门禁和审计事件。

阶段 2 上公网前仍需补：登录失败限速、显式 Origin/CSRF 防护、端到端权限测试和运维监控。SSH 隧道/VPN 内测不必等待这些增强。

### 阶段 3：项目、计划和依赖迁移（已完成）

已实现 `projects/plans/dependencies` 表、团队授权查询、服务端层级和依赖校验、项目级事务锁、乐观并发版本、服务器快照增量 upsert、JSON 显式导入，以及仅在服务器项目为空时出现的本机计划迁移入口。客户端不再从 localStorage 自动恢复计划和依赖。

### 阶段 4：Markdown 和 Entry 迁移（已完成）

已实现 `documents/entries` 表、团队授权 API、Markdown 防抖保存、版本条件和冲突草稿保留、Entry 新增与删除，以及仅在服务器内容为空时出现的本机文档迁移入口。当前保存每份文档和事件的最新版本；有限版本历史仍作为后续增强项。

### 阶段 5：附件能力（核心范围已完成）

已定义 `AttachmentStorage` 并实现本机 Docker 持久卷、附件元数据、SHA-256、团队权限下载、上传/删除审计、单文件 20 MB 限制和团队 1 GB 配额。图片上传后以受保护地址写入 Markdown，不再新增 Base64 图片。当前小团队内测不启用分片直传和病毒扫描；正式公网发布前必须增加异机附件备份、恶意文件检测、限速和生命周期策略，真实规模增长后可把存储实现替换为 S3/OBS。

### 阶段 6：正式公网发布

- 完成 ICP 备案、域名解析和 HTTPS；
- 反向代理只公开 80/443；
- `COOKIE_SECURE=true`；
- 登录限速、账号保护、集中日志、监控告警；
- 数据库定时异机备份及恢复演练；
- 权限隔离、核心 CRUD、旧数据导入和并发冲突验收。

## 3. 为什么不一次性迁移

当前编辑器、计划树、图形依赖和本地备份已经可用。一次性迁移会同时改变身份、存储、协作、部署和运维，回归范围过大。渐进迁移让每个阶段都有可运行版本，也能在真实小团队反馈后再确定附件、历史和权限细度。

## 4. 部署时对阶段 3 的验收标准

- owner 与 member 在不同浏览器登录后看到同一团队项目和计划；
- 非成员无法通过猜测 ID 读取或修改数据；
- 父子层级和依赖不能形成环；
- 两人更新同一计划时不会静默覆盖；
- 页面刷新后数据仍在，localStorage 不再是计划事实源；
- 旧 JSON 可先预览再导入，重复导入不会制造重复数据；
- 迁移前后数量和依赖引用检查一致。
