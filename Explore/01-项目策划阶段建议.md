# 网站项目策划阶段建议

## 1. 文档目的

本文档用于指导 AI 辅助网站项目在进入开发前完成必要的产品策划、需求澄清和技术准备。策划阶段的目标不是一次性预测所有实现细节，而是形成足以支持首轮开发、验收和风险控制的项目事实源。

策划阶段完成后，应能回答以下问题：

- 网站为哪些用户解决什么问题？
- MVP 必须包含哪些能力，明确不包含哪些内容？
- 用户完成核心目标时会经过哪些步骤？
- 每项功能如何判断已经完成？
- 系统涉及哪些关键数据、权限和外部服务？
- 当前有哪些风险、假设和未决问题？
- 第一版如何运行在测试云环境中？

## 2. 核心原则

### 2.1 不追求一次性写出“完整需求”

网站需求会随着原型、用户反馈和技术验证持续变化。策划书应是可版本化、可追踪的动态文档，而不是开发开始后便失效的静态说明。

策划阶段只需要把以下内容做到足够明确：

- 核心目标和成功指标；
- MVP 的范围边界；
- 核心用户流程；
- 可执行的验收条件；
- 影响整体方案的关键技术决策；
- 高风险假设及其验证办法。

未解决的问题应明确记录负责人、验证方式和处理时限，不应通过反复讨论假装已经解决。

### 2.2 先明确业务结果，再讨论实现方式

需求优先描述用户获得的结果，例如“用户可以使用邮箱完成注册”，而不是提前规定“创建 `registerUser()` 函数”。页面、接口、数据库和函数属于实现设计，应在业务目标和验收条件明确后再确定。

### 2.3 固定契约和边界，而非过早固定全部函数

项目开始前值得明确的是：

- 模块职责和依赖方向；
- API 请求、响应和错误格式；
- 数据模型、约束和生命周期；
- 身份认证与权限规则；
- 外部服务边界；
- 性能、安全、可用性和合规要求。

函数名、内部参数和私有模块结构可以在对应功能进入开发时再拆解，避免因过度设计产生大量过期计划。

## 3. 推荐的策划流程

### 阶段一：项目目标与范围

形成项目简述，至少包括：

- 背景和待解决的问题；
- 目标用户及主要使用场景；
- 项目的核心价值；
- MVP 包含的能力；
- MVP 明确排除的能力；
- 成功指标，例如激活率、任务完成率、响应时间或稳定性目标；
- 时间、预算、技术栈、服务器和合规等约束。

建议将需求按以下优先级分类：

- `Must`：MVP 不可缺少；
- `Should`：重要但允许延后；
- `Could`：有价值但不影响首版；
- `Won't now`：当前版本明确不做。

### 阶段二：用户流程与异常场景

为每类用户描述完整流程，包括：

- 进入系统的方式；
- 完成核心任务的正常路径；
- 空状态、错误状态和无权限状态；
- 中断后如何恢复；
- 数据创建、修改、删除和归档过程；
- 管理员或运营人员需要处理的例外情况。

用户流程不应只描述理想路径。登录失败、重复提交、网络中断、无权限访问、资源不存在和外部服务不可用等情况也应纳入设计。

### 阶段三：需求与验收条件

每项功能应以用户结果描述，并附带可观察、可测试的验收条件。

示例：

```yaml
feature: 邮箱注册
user_value: 新用户可以创建账号并进入系统
preconditions:
  - 用户未登录
acceptance_criteria:
  - 合法邮箱和密码可以完成注册
  - 重复邮箱得到明确但安全的错误提示
  - 非法输入不会写入数据库
  - 密码不会以明文保存或出现在日志中
  - 注册成功后按产品规则进入系统或等待验证
out_of_scope:
  - 第三方社交账号登录
```

好的验收条件应能由自动化测试或人工操作明确判断通过或失败，避免“体验良好”“性能较高”等不可验证表述。

### 阶段四：信息架构与界面原型

输出内容包括：

- 页面清单和导航结构；
- 核心页面线框图或交互原型；
- 页面状态，包括加载、空数据、错误和无权限；
- 响应式布局要求；
- 基础视觉规范和组件复用原则；
- 可访问性要求。

原型用于确认用户流程和信息层级，不要求在此阶段完成最终视觉效果。

### 阶段五：架构与关键契约

架构设计应覆盖：

- 前端、后端、数据库、缓存、对象存储及第三方服务的边界；
- 身份认证、会话管理和权限模型；
- API 或事件契约；
- 数据实体、关系、唯一性约束和删除策略；
- 日志、监控、告警和审计要求；
- 数据备份、恢复和迁移策略；
- 开发、测试、预发布和生产环境的差异；
- 部署方式、回滚方式和密钥管理方式。

存在多个可行方案时，应使用架构决策记录（ADR）保存背景、候选方案、最终选择、理由和后果。

### 阶段六：风险原型和最小可运行骨架

在大规模功能开发前，优先验证高风险部分，例如：

- 不熟悉的云平台或运行时；
- 第三方登录、支付或消息服务；
- 高并发、实时通信或大文件处理；
- 复杂权限或数据隔离；
- 关键浏览器兼容性。

随后建立一个最小可运行骨架，至少包括：

- 可访问的基础页面；
- 健康检查接口；
- 最小数据库连接；
- 自动化构建和测试；
- 测试环境部署；
- 基础日志和错误监控。

尽早完成云端测试部署，可以提前暴露域名、HTTPS、反向代理、环境变量、数据库迁移和网络配置问题。

## 4. 推荐的策划产物

建议在仓库中持续维护以下文件：

```text
docs/
├── product-brief.md       # 项目目标、用户和范围
├── requirements.md       # 用户故事与验收条件
├── user-flows.md         # 核心流程和异常路径
├── architecture.md       # 系统结构和模块边界
├── api-contracts.md      # API、事件和错误格式
├── data-model.md         # 数据模型和数据约束
├── security-model.md     # 身份、权限和威胁边界
├── decisions/            # 架构决策记录 ADR
├── deployment.md         # 环境、部署、备份和回滚
└── task-board.md         # 任务、依赖关系和当前状态
```

这些文件共同构成项目的事实源。Agent 开始任务前应读取与任务相关的部分，而不是依赖聊天记录或口头约定。

## 5. 策划阶段退出条件

满足以下条件后即可进入迭代开发，无需等待所有未来需求完全确定：

- 核心用户、核心问题和项目价值明确；
- MVP 包含项与排除项已经确认；
- 核心用户流程和主要异常流程已经描述；
- MVP 功能均具备可测试的验收条件；
- 模块边界、数据边界、权限规则和关键契约已经确定；
- 高风险技术点已经验证或有明确验证任务；
- 测试环境和最小部署方案已经设计；
- 未决问题、假设、负责人和处理方式已经记录；
- 首批纵向功能切片及其依赖关系已经形成。

## 6. 人类必须保留的决策权

AI 可以帮助分析、补充场景和生成方案，但以下事项应由项目负责人确认：

- 产品目标、用户群体和商业边界；
- MVP 的最终范围和优先级；
- 预算与云资源成本上限；
- 隐私、法律和合规要求；
- 高风险架构取舍；
- 生产数据处理规则；
- 生产发布和不可逆操作。

## 7. 常见误区

- 为追求完整而无限延长讨论阶段；
- 在用户流程未确认前就选择大量技术组件；
- 一开始把整个项目拆到函数级，导致计划快速过期；
- 只设计成功路径，不处理错误和恢复流程；
- 把部署、安全、备份和监控留到项目最后；
- 将 AI 生成的策划内容直接视为已经验证的事实；
- 只写功能描述，不写可测试的验收条件。

策划阶段最终交付的不是一份篇幅庞大的说明书，而是一组能够指导实现、限制偏差并支持验收的项目事实。
