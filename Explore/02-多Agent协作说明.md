# 网站开发多 Agent 协作说明

## 1. 文档目的

本文档用于指导主 Agent 和子 Agent 协作开发、测试、审查并部署网站项目。核心目标是降低上下文丢失、重复劳动、代码冲突和集成失败风险，使每个任务都有明确输入、修改边界、验收证据和责任归属。

推荐采用“主 Agent 编排 + 按需创建专业 Agent + 自动化质量门禁 + 人工控制高风险操作”的模式。

## 2. 任务拆分原则

### 2.1 使用三层任务结构

#### 第一层：业务里程碑

描述用户最终可以完成什么，例如：

- 用户能够注册、登录和退出；
- 用户能够创建并发布内容；
- 管理员能够审核内容；
- 网站能够稳定部署到生产环境。

#### 第二层：纵向功能切片

每个切片覆盖完成一项用户能力所需的前端、接口、数据和测试。例如：

> 完成“用户使用邮箱注册”功能，包括注册页面、注册接口、用户表变更、密码安全处理、输入校验、错误提示和自动化测试。

一个合格的纵向切片应尽量满足：

- 能够独立开发、测试和演示；
- 修改范围明确；
- 与其他任务依赖较少；
- 合并后主分支仍可构建和运行；
- 通常可在一个较短的 Agent 工作周期内完成。

默认按纵向功能切片分工，而不是长期按前端、后端、数据库工种分工。只有在接口契约已经稳定且工作确实独立时，才拆成多个技术任务并行实施。

#### 第三层：实现清单

切片即将实施时，再拆分为：

- 页面和组件；
- API 路由和输入输出类型；
- 数据模型和迁移；
- 服务函数；
- 单元、集成和端到端测试；
- 配置、监控和文档变更。

函数级设计应属于当前切片的短期实现计划，不应成为整个项目一开始就固定的总计划。

### 2.2 使用依赖图管理并行

任务只有在不存在未完成的前置依赖、不会争用同一核心文件且契约稳定时才能并行。

适合并行的工作包括：

- 互不依赖的功能切片；
- 多个独立技术方案的调研；
- 已有稳定 API 契约的前端和后端实现；
- 实现、测试补充和文档编写；
- 独立模块的安全、性能和可访问性审查。

不适合并行的工作包括：

- 多个 Agent 同时修改同一核心模块；
- 数据模型未确定时开发多个依赖功能；
- API 持续变化时分开实现前后端；
- 一个任务的输出是另一个任务的必要输入；
- 需要所有参与者持续共享完整上下文的强耦合重构。

多 Agent 数量应由任务依赖图决定。小型网站通常同时使用一个主 Agent、一至两个实现 Agent和一个审查或测试 Agent即可。

## 3. Agent 角色与职责

### 3.1 主 Agent：编排者

主 Agent 负责：

- 维护项目目标、事实源和任务状态；
- 检查任务是否达到可开始条件；
- 分析依赖并决定串行或并行；
- 为子 Agent 创建标准任务包；
- 限定允许修改和禁止修改的文件范围；
- 汇总子 Agent 的实际产物；
- 检查代码差异并运行集成验证；
- 派发针对性修复任务；
- 判断是否允许合并或进入下一阶段；
- 在高风险操作前把控制权交还给人类。

主 Agent 不应仅根据子 Agent 的文字汇报判断任务完成，必须检查文件差异、测试结果、构建结果和实际运行行为。

### 3.2 产品/需求 Agent

按需负责：

- 澄清用户流程和业务规则；
- 发现遗漏的异常场景；
- 编写和检查验收条件；
- 判断实现是否偏离产品目标。

### 3.3 架构 Agent

适用于：

- 项目初始化；
- 引入新的核心模块或外部服务；
- 数据模型或权限模型发生重大变化；
- 出现跨模块技术决策；
- 性能、安全或扩展性需要重新设计。

小功能无需反复触发完整架构设计。架构 Agent 的结论应写入架构文档或 ADR，而不是只保存在对话中。

### 3.4 功能实现 Agent

负责一个完整纵向切片，并应：

- 阅读相关需求、架构和契约；
- 在限定范围内完成代码和测试；
- 运行规定的验证命令；
- 报告修改文件、设计取舍、测试结果和遗留风险；
- 不擅自扩大功能范围或修改无关模块。

### 3.5 独立审查 Agent

应由不同于实现者的 Agent 承担，负责：

- 对照验收条件检查需求覆盖；
- 检查边界条件、错误处理和恢复流程；
- 检查安全、性能和可维护性；
- 检查测试是否真正验证行为；
- 发现重复实现、架构偏移和兼容性问题；
- 给出具体、可定位、可验证的修改意见。

审查 Agent 默认只提出问题，不应在未授权时同时大规模重写实现，以免责任边界模糊。

### 3.6 运维/发布 Agent

负责：

- 容器、基础设施即代码和 CI/CD；
- 云服务器与运行环境配置；
- 环境变量和密钥引用；
- 日志、监控和告警；
- 数据库备份、恢复和迁移流程；
- 测试环境发布、生产发布方案和回滚验证。

该角色应从最小可运行骨架阶段参与，而不是等功能全部完成后再处理部署。

## 4. 标准任务包

主 Agent 向子 Agent 派发任务时，应提供结构化任务包：

```yaml
task_id: AUTH-003
title: 实现邮箱密码登录
goal: 用户可以使用邮箱和密码登录并进入控制台
business_context: 未登录用户不能访问控制台

dependencies:
  - AUTH-001
  - DB-002

references:
  - docs/requirements.md#login
  - docs/api-contracts.md#login
  - docs/security-model.md#authentication

allowed_files:
  - src/features/auth/**
  - tests/auth/**
  - migrations/**

do_not_change:
  - src/billing/**
  - deployment/production/**

acceptance_criteria:
  - 正确账号能够登录
  - 错误凭据返回统一错误，不泄露账号是否存在
  - 连续失败受到频率限制
  - 登录状态在刷新后保持
  - 未登录用户访问控制台时跳转到登录页

required_verification:
  - lint
  - typecheck
  - unit tests
  - API integration tests
  - production build

deliverables:
  - 修改文件列表
  - 实现说明和关键取舍
  - 验证命令及实际结果
  - 已知限制和遗留风险
  - 数据或配置变更的回滚方法
```

其中最重要的是：

- `goal`：说明期望结果，而不是只列动作；
- `references`：提供必要上下文的唯一来源；
- `allowed_files`：降低并行修改冲突；
- `do_not_change`：阻止范围蔓延；
- `acceptance_criteria`：定义完成；
- `required_verification`：要求可复查证据；
- `deliverables`：让成果能够被主 Agent 接管。

## 5. 单个功能的执行循环

1. 主 Agent 检查任务依赖、契约和验收条件是否齐全。
2. 主 Agent 选择合适角色，派发标准任务包。
3. 实现 Agent 在独立分支或工作区完成代码和自测。
4. 实现 Agent 返回实际变更、测试结果和风险，不只返回完成声明。
5. 独立审查 Agent 对照需求、架构和代码差异审查。
6. 主 Agent 运行或检查 CI、集成测试和构建结果。
7. 未通过时创建范围明确的修复任务，禁止无边界地反复重做。
8. 通过后合并小型 PR，并部署到测试环境。
9. 在测试环境执行端到端验收和必要的人工检查。
10. 更新任务状态、项目文档和架构决策记录。

任务完成必须同时满足：代码已产生、验收条件已覆盖、必要测试已通过、文档已同步、风险已记录、主分支仍可运行。

## 6. 代码与上下文隔离

### 6.1 代码隔离

- 每个任务使用短生命周期分支或独立工作区；
- 一个 PR 尽量只实现一个可描述的业务结果；
- 避免多个 Agent 同时修改共享配置、核心类型或同一迁移文件；
- 共享文件需要指定唯一负责人，其他 Agent 通过明确请求协调；
- 频繁集成，避免长期分支在最后集中合并；
- 禁止子 Agent 直接向生产分支推送。

### 6.2 上下文隔离

不要把整个项目和全部历史对话复制给每个 Agent。任务上下文应包含：

- 当前任务目标；
- 相关需求和验收条件；
- 必要的架构与接口契约；
- 允许修改的文件范围；
- 前置任务的已确认产物；
- 必须运行的验证；
- 明确的禁止事项。

跨任务的长期知识必须写回仓库文档。聊天记录可以辅助理解，但不应成为唯一事实源。

## 7. 四层质量门禁

### 第一层：实现 Agent 自检

- 对照验收条件逐项检查；
- 运行指定测试；
- 查看实际差异；
- 报告失败项和未覆盖风险。

### 第二层：独立 Agent 审查

- 需求正确性；
- 架构一致性；
- 安全和权限；
- 边界条件；
- 测试有效性；
- 可维护性和兼容性。

### 第三层：自动化 CI

至少应包含：

- 格式和 lint；
- 静态类型检查；
- 单元测试；
- API 或数据库集成测试；
- 生产构建；
- 依赖和代码安全扫描。

根据项目风险增加端到端、性能、可访问性和数据库迁移测试。保护主分支，要求必要检查通过后才能合并。

### 第四层：人工验收

人类重点确认：

- 产品方向和交互体验；
- 关键业务规则；
- 成本和资源变化；
- 数据迁移和不可逆影响；
- 生产环境发布。

## 8. 云部署与生产安全

建议至少区分：

- 本地开发环境；
- 自动化测试环境；
- 共享测试或预发布环境；
- 生产环境。

生产环境必须遵守：

- 密钥通过云平台或 CI/CD 的密钥系统注入，不进入代码、任务描述或日志；
- 数据库迁移必须有兼容性、备份和回滚方案；
- 部署必须产生可追踪版本；
- 发布前运行必要检查；
- 发布后检查健康状态、错误率和核心业务流程；
- 保留上一稳定版本的快速回滚能力；
- 删除资源、扩大费用、修改访问控制等操作需要人工批准。

Agent 可以自动完成开发、测试、创建 PR、部署临时环境和提交发布申请。以下操作默认需要人类授权：

- 创建明显增加费用的云资源；
- 修改生产数据库结构或数据；
- 删除数据、服务器或基础设施；
- 修改域名、证书和生产访问控制；
- 接触或迁移生产密钥；
- 绕过失败的质量门禁；
- 正式生产发布。

## 9. 主 Agent 的调度规则

主 Agent 每次调度前应依次判断：

1. 任务是否有明确且可验证的结果？
2. 前置依赖是否全部完成并经过验收？
3. 接口和数据契约是否足够稳定？
4. 是否会与运行中的任务修改同一文件或同一数据边界？
5. 是否值得使用新 Agent，还是单一 Agent 连续完成更高效？
6. 子 Agent 是否获得了必要但不过量的上下文？
7. 是否存在需要人工批准的权限、费用或不可逆操作？

出现以下情况时应停止派发并先解决阻塞：

- 验收条件互相矛盾；
- 架构文档和实际代码不一致；
- 多个任务争用同一核心模块；
- 上游接口仍在频繁变化；
- 测试环境无法稳定运行；
- 任务需要超出既定范围或新的外部权限。

## 10. 项目级工作流

```text
项目目标与 MVP 边界
        ↓
用户流程与验收条件
        ↓
架构边界、数据模型和接口契约
        ↓
最小可运行骨架及测试环境部署
        ↓
建立纵向功能切片和任务依赖图
        ↓
主 Agent 创建并派发任务包
        ↓
实现 Agent 开发与自测
        ↓
独立 Agent 审查
        ↓
CI 自动验证
        ↓
合并并部署测试环境
        ↓
端到端和人工业务验收
        ↓
人工批准生产发布
```

## 11. 建议跟踪的指标

为了判断多 Agent 是否真正提升效率，可持续记录：

- 每个任务从开始到验收的时间；
- 首次审查通过率；
- 因需求不清导致的返工比例；
- 合并冲突次数；
- CI 失败原因分布；
- 测试环境发现的问题数量；
- 生产缺陷和回滚次数；
- 每个功能涉及的 Agent 交接次数；
- Agent 成本与人工节省时间。

如果交接次数、冲突和返工持续增加，应减少并行 Agent 数量、缩小任务范围或先稳定共享契约。

## 12. 核心准则

- 以可验收的业务结果拆任务，不以技术工种机械拆任务；
- 先确定模块边界和契约，不提前设计全部函数；
- 只并行真正独立的任务；
- 每个 Agent 都必须有清晰的上下文、文件边界和完成定义；
- Agent 的汇报不是证据，代码差异、测试和运行结果才是证据；
- 实现者与审查者尽量分离；
- 尽早建立云端可运行骨架；
- 自动化负责重复检查，人类保留产品和高风险操作的最终决定权；
- 所有可复用结论必须写回项目事实源，不能只存在于对话中。
